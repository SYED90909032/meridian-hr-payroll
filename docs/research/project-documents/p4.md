
## Using the customer's Google Workspace or Microsoft 365 subscription

Most customers already pay for one of these suites. Business Standard costs about US$14 per user per month on both, and Business Plus or Business Premium about US$22 [[g:24]] [[ms:26]]. Meridian is designed to reuse that spend instead of rebuilding it. The integration covers six capabilities, and each uses the narrowest permission that works.

**Sign-in.** Employees sign in with their existing Google or Microsoft work account. For Microsoft, Meridian is registered as a multi-tenant Entra application. It validates each token against the customer's tenant ID (`tid`), so Conditional Access policies such as MFA or compliant devices apply automatically [[ms:11]] [[ms:14]]. For Google, it uses OpenID Connect and keys every account on the stable `sub` identifier, not on the email address, which can change [[g:6]]. The `hd` parameter steers sign-in to the right Workspace domain, but the domain is still verified on the server.

**Provisioning.** On Microsoft, Entra pushes users and groups to Meridian's SCIM 2.0 endpoint [[ms:13]]. On Google, Meridian syncs through the Directory API with admin approval [[g:11]]. Meridian can also run the other way and create accounts from HR data, as described under onboarding.

**Storage.** Documents, exports, letters and continuity kits go to the customer's Drive, shared drives, SharePoint or OneDrive. Meridian uses `drive.file` with Google Picker on Google and `Sites.Selected` on Microsoft [[g:12]] [[ms:22]]. Copilot respects Purview sensitivity labels, and Meridian can apply a label to the HR folders it creates [[ms:25]].

**Mail.** Meridian uses `gmail.send` or `Mail.Send` for personal, low-volume notices, and routes bulk sends through SES because of the daily limits on both suites [[g:17]] [[g:18]] [[ms:15]] [[ms:17]].

**Calendar, meetings and chat.** Scheduling uses Google Calendar and Meet or Microsoft Calendar and Teams. Approvals use Google Chat cards or Teams Adaptive Cards [[g:21]] [[g:23]] [[ms:18]] [[ms:21]].

**AI the customer already licenses.** This works differently on each suite.

- **Microsoft Copilot.** Meridian ships a declarative agent for Microsoft 365 Copilot that uses Meridian's remote MCP server as its action, declared in the plugin's `agentConnectors` with OAuth [[ms:1]] [[ms:4]]. For live HR and payroll data Meridian uses a **federated** connector, which queries Meridian through MCP at question time instead of copying data into Microsoft Graph. Microsoft describes federated connectors as the right fit for live or sensitive data [[ms:2]] [[ms:3]]. Only non-sensitive content with exact item-level permissions, such as the published policy handbook, is offered as a synced connector, because wrong permissions on synced items can expose HR data to the wrong employees [[ms:3]] [[ms:25]]. Copilot Studio users can add the same MCP server through its wizard, which supports the Streamable HTTP transport and OAuth 2.0 [[ms:6]]. Distribution starts with each customer's own app catalogue and later moves to the Microsoft Marketplace after Microsoft's review [[ms:8]] [[ms:10]].
- **Google Gemini.** For customers with Gemini Enterprise, Meridian is added as a custom MCP server data store, a generally available feature that the customer's admin must enable [[g:3]] [[g:4]]. Registering Meridian as an A2A agent in Gemini Enterprise is still in preview, so it is offered as an option, not a commitment [[g:5]]. Plain Gemini inside Gmail and Docs has no documented way for a third-party app to extend it. Meridian therefore reaches those users through a Workspace add-on and a Google Chat app, published on the Workspace Marketplace after Google's review [[g:1]] [[g:2]] [[g:7]].

The pitch to the customer is straightforward: Meridian reuses the identity, storage, mail, calendar, chat and AI licences they already have. It does not resell Copilot Studio capacity, which Microsoft prices separately at US$200 for 25,000 credits a month, and it does not promise features the suites do not offer, such as central Outlook signatures through Graph [[ms:28]] [[ms:16]].

**Verification and review costs to plan for.** Public Google apps that use sensitive scopes such as `gmail.send` need OAuth verification. Apps that store restricted-scope data on a server, for example `gmail.settings.basic` for signatures, need an annual security assessment under Google's CASA framework [[g:7]] [[g:13]]. To keep the core app on non-sensitive and sensitive scopes only, the signature manager uses the customer-granted service-account path. Whether that path also triggers the assessment must be confirmed with Google before launch.

## Connecting the customer's own AI: ChatGPT, Claude, Gemini, Copilot or any model

![AI and MCP plane](/home/ubuntu/hr_research/v2/diagrams/ai_plane.png)

There are two separate ways to connect, and Meridian supports both.

**Mode 1: the assistant comes to Meridian (MCP).** The customer uses the assistant they already pay for, and connects Meridian as a tool through MCP (Model Context Protocol, an open standard that lets AI assistants call external tools). Meridian never sees the customer's model key in this mode. The assistant signs in to Meridian with OAuth as the individual user, and Meridian applies that user's permissions to every call.

- **ChatGPT Business and Enterprise** support custom remote MCP apps. Admins create and publish them. Newly discovered actions start disabled, and changes to the tool list appear as a diff for the admin to approve. That diff guards against a server silently changing its tools [[llm:1]]. ChatGPT reaches only remote servers, so Meridian's MCP server is public HTTPS. Customers who want a private endpoint can use OpenAI's Secure MCP Tunnel [[llm:1]]. OpenAI states that it does not train on Business or Enterprise data by default [[llm:2]].
- **Claude** supports custom remote connectors on all plans, including one on the Free plan. Connections are made from Anthropic's cloud, so Meridian must accept traffic from Anthropic's published IP ranges. Owners can set each tool to Always allow, Needs approval or Blocked, so a customer can block write tools centrally [[llm:3]] [[llm:5]].
- **Copilot Studio and Gemini Enterprise** connect as described in the previous section [[llm:6]] [[llm:8]].
- **Developer tools** such as VS Code and Cursor can use the same server for HR operations teams that work there [[llm:9]] [[llm:10]].

**Mode 2: Meridian uses the customer's model (bring your own key).** Inside Meridian's own assistant, the customer can choose a model provider and enter an API key, or a cloud credential for Azure OpenAI, Amazon Bedrock or Google Vertex AI. The key is stored in Meridian's vault, encrypted with the tenant's key. It is used only by the model router and is never shown to any model or user after entry. Each key has its own model allow-list, monthly budget and rate limit. Azure's standard inference is stateless and does not train on prompts, and Bedrock lets the customer set data retention to none, so customers can choose the provider whose terms match their policy [[llm:14]] [[llm:15]]. Gateways such as Cloudflare AI Gateway or LiteLLM supply budgets, rate limits and caching [[llm:16]] [[llm:17]]. Meridian turns off raw prompt logging in the gateway and isolates any cache per tenant, because a shared cache could return one tenant's answer to another [[llm:17]].

## MCP server design and the no-leak data firewall

### Protocol and authorisation

Meridian runs one remote MCP endpoint per regional cell, for example `https://mcp.eu.meridian.example/mcp`, over Streamable HTTP. Copilot Studio no longer supports the older SSE transport, so Streamable HTTP is the one to build [[ms:6]]. The design follows the current MCP specification, version 2026-07-28 [[llm:11]]:

- Meridian runs its own OAuth 2.1 authorisation server, with the authorisation-code flow and PKCE (proof key for code exchange) required.
- The MCP server publishes Protected Resource Metadata (RFC 9728), so clients discover the authorisation server automatically.
- Clients register with Client ID Metadata Documents. Dynamic Client Registration stays available only for hosts that still need it, because the specification now marks it deprecated.
- Every token is bound to Meridian's MCP address as its audience through resource indicators (RFC 8707). The server checks signature, issuer, expiry, audience, tenant, user and scope on every request.
- Meridian never accepts a token issued for another service and never passes the assistant's token on to anything else. Calls to internal services use a separate, narrowly scoped internal credential [[llm:11]] [[llm:12]].
- Refresh tokens (`offline_access`) are issued for long-lived connections, as ChatGPT recommends [[llm:1]]. They are rotated on every use, revoked when the employee leaves, and limited in lifetime by tenant policy.
- Redirect URIs must match exactly, state is required, and every URL inside metadata is fetched through an SSRF-safe fetcher that blocks private network addresses [[llm:12]].

### Tools in four tiers

Tools are grouped into four tiers. Each tier is a separate OAuth scope, so a customer can grant a host only the tiers it needs.

1. **Read** tools fetch facts the user may see, such as `get_leave_balance`, `list_missing_documents` and `get_policy_answer`.
2. **Analyse** tools return aggregates, such as `headcount_by_department` and `overtime_trend`. They have a minimum group size of five and never return individual restricted fields.
3. **Draft** tools prepare a change without applying it, such as `draft_leave_request`, `draft_letter_batch` and `draft_announcement`. They return a draft ID and a preview.
4. **Commit** tools apply a draft by its ID, such as `submit_draft`. Commits are idempotent, run under the user's permissions, and anything high-impact, such as pay changes, bulk messages or terminations, goes to Meridian's approval inbox, where a second person must approve. Meridian never relies on the AI host's own confirmation prompt as its only control [[llm:1]].

There is deliberately no tool that runs arbitrary queries, fetches arbitrary URLs or exports whole tables. Bulk exports remain a Meridian feature with its own permission and audit.

### Signed, pinned tool manifests

Every tool's name, description, input schema and output schema is part of a signed manifest with a version number. Tool descriptions are fixed text written by Meridian, never generated from tenant data. When a new version adds or changes a tool, the tenant admin sees a diff and must approve it before the tool becomes available to their users. This mirrors what ChatGPT Enterprise does on its side, and it closes the "rug pull", where a tool changes behaviour after approval [[llm:1]] [[llm:12]].

### The data firewall

Every tool response and every prompt from the in-app assistant passes through one policy component before leaving Meridian. It applies five rules in order.

1. **Field class rules.** `restricted` fields (bank account, national ID, exact salary) and `special` fields (health, biometrics, disciplinary records) are never sent to an external assistant by default. A tenant can allow a specific class for a specific role and a specific host, such as salary to the payroll approver in Claude Enterprise. That exception is recorded and shown in the connector settings.
2. **Minimisation.** Tools return only the fields their schema declares, never whole employee records [[llm:13]].
3. **Pseudonymisation.** Where policy requires it, people are replaced with tenant-scoped tokens such as `EMP_7F2A`, generated with a keyed hash so they cannot be guessed. The mapping never leaves Meridian [[llm:22]]. Each token comes with a **sealed reference**, a Meridian link that shows the real person only after the user signs in to Meridian. The assistant can therefore say "EMP_7F2A has three missing documents", and the user clicks through to see who it is.
4. **Output scanning.** A PII detector such as Microsoft Presidio scans free text, such as case comments and survey answers, for names, phone numbers, IDs and account numbers that slipped into fields. Matches are masked [[llm:22]] [[llm:23]]. Employee-written text is wrapped and labelled as untrusted data, so an instruction hidden inside a helpdesk comment is treated as text, not as a command [[llm:13]].
5. **Rate and volume limits.** Each user, host and tool has a call budget and a records-returned budget. A pattern that looks like scraping, such as hundreds of profile reads in a minute, is throttled and raised as a security alert.

Every call is audited with tenant, user, host, tool, policy decisions, record counts and hashes of the inputs and outputs. The raw content is never logged. The same firewall protects the in-app assistant, so there is one rule set to test.

### Testing the AI surface

The MCP server and assistant have their own test suite: cross-tenant access attempts, prompt-injection payloads planted in employee text, tool-description tampering, oversized responses, token-audience mismatches, and expired or revoked tokens. The suite runs on every change, and a red-team review happens before each new tool tier is enabled, in line with OWASP's guidance on prompt injection and excessive agency [[llm:13]].
